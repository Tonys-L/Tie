拆分 commands.rs — 按业务域切分 + 提取 image_service

Strong
Files
src-tauri/src/application/commands.rs (814 行)
Domain
便签管理 / 提醒调度 / 数据同步 / 便签模板 / AI 嗅探
Problem

44 个 Tauri 命令横跨 10 个业务域挤在单文件。文件内还夹杂不属于命令层的逻辑：图片生命周期管理（extract_image_filenames / cleanup_removed_images，行 443-499）、农历计算（get_lunar_dates 直接调用 tyme4rs，行 287-314）、AI 响应解析工具（extract_json_array，行 711-720）。这些是隐藏的领域，没有自己的模块名。

Solution

按业务域拆分为 6 个命令文件：note_commands.rs / reminder_commands.rs / template_commands.rs / sync_commands.rs / ai_commands.rs / system_commands.rs（tray/locale/datadir）。同时提取 image_service.rs 承载图片解析+清理+持久化，update_note_content 命令调用它而非内联。农历计算下沉到 lunar_calendar.rs。

Benefits
  • Locality：图片管理逻辑集中在一处，update_note_content 的孤儿图片清理 bug 只需查一个文件
  • Leverage：未来新增图片格式支持、批量清理等场景有明确入口
  • Tests：image_service 可独立单测（不依赖 Tauri AppHandle）
  • AI 可导航性：每个文件 <200 行，AI 修改某业务域时无需读 814 行

候选 2

合并 reminder_scheduler + reminder_service — 单一深化模块

Strong
Files
reminder_scheduler.rs (166 行) + reminder_service.rs (125 行)
Domain
提醒调度 (Reminder Scheduling)
Problem

reminder_scheduler::check_and_fire 只是单行 pass-through 调用 reminder_service::fire_reminders。两个文件强耦合但分散，理解"提醒如何触发"需在 3 个文件间跳转（scheduler → service → window_manager + lunar_calendar）。删除测试：check_and_fire 删除后复杂度完全消失——典型 pass-through。

Solution

合并为单一 reminder_scheduler.rs，承载完整调度链路：定时器 + Notify 机制 + 到期检查 + 触发编排（通知 + 弹窗 + 状态更新）+ LunarMonthly 农历计算 + 窗口激活。外部只暴露 start() / notify_changed() / fire_now() 三个方法。

Benefits
  • Locality：所有"提醒何时触发"逻辑集中一处
  • Depth：小接口（3 方法）背后承载完整调度行为
  • Tests：可直接对合并后的模块单测"假定时器 + 假 repo"验证触发链路
  • 符合 glossary.md 中"调度器 (Scheduler)"词条的本意（"事件驱动调度...触发通知 + 弹出便签窗口"）

候选 5

分解 git_sync sync 方法 — 200 行单方法按阶段切分

Worth exploring
Files
src-tauri/src/application/git_sync.rs:48-245
Domain
数据同步 (Data Sync)
Problem

单个 sync 方法 200 行，承担 10 个步骤：配置加载/验证 → 分支名校验 → git config → remote 设置 → fetch → 远程 ref 验证 → merge（含 unrelated histories + 冲突解决）→ JSON 导入 → JSON 导出 → commit → push 安全检查 → push → 状态消息。错误处理嵌套深，难以单测某一阶段。INV-024/025 的"先拉后推"约束全部在这一个方法里验证。

Solution

提取私有阶段函数：validate_config() / prepare_remote() / fetch_and_merge() / sync_data_bidirectional() / commit_and_push()。sync 方法变为编排：5 行调用 5 个阶段函数，每阶段返回 Result<StageOutput, String>。

Benefits
  • Locality：每阶段错误处理局部化
  • 可测试性：可单测 fetch_and_merge 的冲突场景（注入 mock git_ops）
  • INV 验证：INV-024/025 的断言可放在对应阶段函数中，违反时立即 panic
  • 不改变对外接口（sync 签名不变），无破坏性
Before / After
Before — 单方法 200 行
fn sync() {
  // L48-66: 配置加载验证
  // L67-89: 分支名校验
  // L90-105: git config
  // L106-120: remote 设置
  // L121-140: fetch
  // L141-160: 远程 ref 验证
  // L161-200: merge (复杂)
  // L201-220: JSON 导入
  // L221-230: JSON 导出
  // L231-240: commit + push 检查
  // L241-245: push + 消息
}
After — 5 阶段函数 + 编排
fn sync() {
  let cfg = validate_config()?;
  let remote = prepare_remote(&cfg)?;
  let merge = fetch_and_merge(&cfg)?;
  let data = sync_data_bidirectional()?;
  commit_and_push(&cfg, &data)?;
  Ok(sync_summary(...))
}

fn validate_config() -> Result<Cfg>
fn prepare_remote() -> Result<Remote>
fn fetch_and_merge() -> Result<Merge>
fn sync_data_bidirectional() -> Result<Data>
fn commit_and_push() -> Result<()>
候选 6

Suggestion 联合类型 — 替换 any，获得类型安全

Worth exploring
Files
src/types.ts:84 + src/main.ts:1770-1790
Domain
AI 嗅探 (AI Sniff)
Problem

Suggestion.data: any 丢失了后端 5 种建议类型的类型信息。前端 executeSuggestion 需类型断言：suggestion.data as SniffResult、suggestion.data as string[]。新增建议类型时无编译期检查，遗漏分支只能运行时发现。

Solution

改为 discriminated union：

type Suggestion =
  | { type: 'reminder'; data: SniffResult }
  | { type: 'todo_split'; data: string[] }
  | { type: 'tidy'; data: string }
  | { type: 'style'; data: { style_type: string; styled_text: string } }
  | { type: 'tag_suggest'; data: string[] }
  | { type: string; data: unknown };
Benefits
  • 类型安全：编译期检查 executeSuggestion 分支完整性
  • IDE 自动补全：在 case 'reminder': 分支内 data 自动推断为 SniffResult
  • 扩展安全：新增建议类型时 TS 编译器提示未处理分支
  • 低成本：仅 types.ts + executeSuggestion 函数签名变更
候选 7

hub.ts 批量恢复 N+1 + 批量 unarchive 命令补全

Speculative
Files
src/hub.ts:1268-1276 + src-tauri commands.rs
Domain
便签管理 (Note Management)
Problem

批量操作有 batch_archive_notes / batch_delete_notes / batch_update_color 3 个命令，但缺 batch_unarchive_notes。hub.ts 用 Promise.all(ids.map(id => api.unarchiveNote(id))) 模拟，100 张便签 = 100 次 IPC。注释"暂无 batch_unarchive 命令"明示 API 不对称。

Solution

后端补 batch_unarchive_notes(ids: Vec<String>) 命令，复用现有批量命令模式。前端改用单次 IPC 调用。

Benefits
  • 性能：100 次 IPC → 1 次，UI 响应快
  • API 对称性：archive/unarchive 成对
  • 低成本：~30 行代码

🎯 Top Recommendation

如果只做一件事，先做 候选 2：合并 reminder_scheduler + reminder_service。

成本
低
合并 2 文件，无新接口
收益
高
消除 pass-through，理解摩擦 -50%
风险
极低
单调用方，无破坏性
理由：这是唯一一个"删除测试"明确通过的候选——check_and_fire 是纯 pass-through，合并后复杂度直接消失。其他候选（拆分大文件）虽然收益更高，但成本也高，且会触发 constraints.md 约束更新。候选 2 是无约束冲突、低成本、高 locality 收益的"快速胜利"。
后续顺序建议：候选 2 → 候选 6（类型安全，低成本） → 候选 5（git_sync 阶段化，无破坏） → 候选 1（commands.rs 拆分，需更新约束） → 候选 3（共享 UI 层） → 候选 4（main.ts 拆分）
